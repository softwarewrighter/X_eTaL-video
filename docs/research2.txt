X_eTaL Academy: A Complete Video Course in Array Programming
Curriculum design • Narration scripts • Animated explanations • Executable examples • Remotion + VoxCPM production

I would build this as a progressive educational series that starts by teaching people to think in arrays, then teaches X_eTaL as a language, and ultimately uses X_eTaL to explore increasingly sophisticated computing concepts.

The course should work for several audiences: programmers coming from C, Rust, JavaScript, or Python; people interested in APL, J, K, or BQN; students learning functional programming; and more advanced developers interested in compilers, GPUs, FPGAs, and machine learning.

One important distinction: we should teach array programming before teaching X_eTaL syntax. The first videos should change how students approach problems, rather than immediately introducing unfamiliar notation.

3. Teaching style and visual language
The course should have a consistent visual grammar. Students should recognize a scalar, vector, function, reduction, or pipeline before reading the accompanying explanation.

Example: From scalar operations to whole-array operations

Explicit iteration controls each operation.
ARRAY THINKING


One operation describes the transformation.
In Remotion, animate the left cells sequentially and the right cells together. This contrasts the programming models without implying that an array implementation necessarily executes all elements simultaneously.

I would use a small, consistent set of visual conventions: blue for built-in functions, green for user-defined functions, cyan for library functions, violet for macros, amber for mutable state or effects, and neutral colors for data. This also aligns with the visual distinction between names in the X_eTaL editor.

Importantly, X_eTaL already has a browser playground with ASCII source, typographically decorated rendering, Run, Notebook, and Step modes. It also has real libraries, including plotting, matrices, statistics, graphs, and equation notation. Those are better teaching assets than hypothetical examples.

4. Detailed scripts and storyboards: opening episodes
Below are production-oriented scripts for the opening sequence. The narration passages are intended to be spoken verbatim, while the scene descriptions specify what Remotion should animate. The short code snippets in the introductory lessons are deliberately language-neutral; X_eTaL examples are introduced when the syntax itself becomes the subject.

Video 01 — Why Another Programming Language?
Target: 8 minutes · Audience: programmers of any background

Learning objective: Understand what an array language is, why it is different from conventional programming languages, and what X_eTaL is trying to accomplish.

Why Not COBOL? | Andrew C. Young

Scene 1 · 0:00–0:55 — A different way of thinking

Visual: Vintage terminal dissolves into a modern editor. A loop transforms into an array expression.

Narration: “Most programming languages teach us to think in individual steps. Initialize a variable. Enter a loop. Read an element. Perform an operation. Store the result. Repeat. But what if we could describe the entire computation instead of every step required to perform it? That is the central idea behind array programming.”

Scene 2 · 0:55–2:20 — The scalar programming model

Visual: Display a Rust loop. Highlight the index, the data access, the operation, and the append.


let values = [1, 2, 3, 4];
let mut result = Vec::new();

for x in values {
    result.push(x * 2);
}

Narration: “This Rust program doubles four numbers. It is straightforward and correct. But notice how much of the program is about the mechanism. We create storage, iterate over the values, and append the results. The actual mathematical operation is just multiplication by two. In an array-oriented language, we want to make that operation the focus.”

Scene 3 · 2:20–3:40 — Whole-array operations

Visual: Four numbers become four transformed numbers in a single animated operation. Then repeat with 100 numbers.

Narration: “An array language lets us operate on collections as values. Instead of explicitly describing a loop, we describe the transformation. The same idea applies to four values, four thousand values, or a multidimensional array. The language takes responsibility for the mechanics, subject to its defined array and shape rules.”

Scene 4 · 3:40–5:00 — Where array languages came from

Visual: A timeline from APL through J, K, and BQN to X_eTaL, with each language's characteristic notation.

Narration: “Array programming has a long history. APL introduced a powerful mathematical notation for working with entire arrays. Languages such as J, K, and BQN explored different ways to make those ideas expressive and composable. X_eTaL builds on that tradition while exploring static typing, readable typography, functional composition, and modern tooling.”

Scene 5 · 5:00–6:45 — Why X_eTaL?

Visual: Show ASCII source transforming into decorated X_eTaL, then demonstrate the browser editor.

Narration: “X_eTaL is short for eXperimental Extensible Typed Array Language. It is implemented in Rust, but the language itself follows the array programming tradition. Source code is plain ASCII, yet it can be rendered with meaningful typography. Functions are visually distinguished from variables. Axes and exponents can be expressed through decoration. And types are checked statically, without requiring us to write type annotations everywhere.”

Scene 6 · 6:45–8:00 — What you will learn

Visual: A montage of array transformations, type inference, macros, plotting, GPU kernels, FPGA diagrams, and neural networks.

Narration: “We'll begin with the fundamentals: arrays, shapes, functions, and composition. Then we'll learn how to write X_eTaL programs, build libraries, and extend the language. Eventually, we'll use those same ideas to explore graphics, games, parallel hardware, machine learning, and fine-tuning. But first, we need to learn how to stop thinking one element at a time.”

End-of-video exercise: Ask students to identify which parts of a conventional loop describe the computation and which parts merely control iteration.

Video 03 — Shape, Rank, Axes, and Dimensions
Target: 10 minutes

This is one of the most important lessons in the entire course. I would give it particularly strong 2D and 3D animation.

Scene 1 — What is a scalar?

Narration: “A scalar is a single value. It has no array axes. Its rank is zero, and its shape is an empty sequence of dimensions.”

Scene 2 — What is a vector?

Narration: “A vector is an array with one axis. A vector containing five values has rank one and shape five. The rank tells us how many axes exist; the shape tells us how large each axis is.”

Scene 3 — What is a matrix?

Narration: “A matrix has two axes, conventionally rows and columns. A matrix with three rows and four columns has shape three by four. It contains twelve elements, but its rank is two, not twelve.”

Scene 4 — Higher-dimensional arrays

Narration: “We can add another axis. A collection of two matrices, each three by four, forms an array of shape two by three by four. This is a rank-three array. Higher ranks follow the same principle.”

Scene 5 — Why shape matters

Narration: “Shape is not just metadata. It determines which operations make sense. Two arrays may have compatible shapes for an operation, or they may require explicit reshaping or another transformation.”

Scene 6 — A shape challenge

Narration: “Consider an image with height 480, width 640, and three color channels. What is its shape? What is its rank? And what happens if we add a batch axis for 32 images?”

Video 04 — Mapping, Filtering, and Reducing
Target: 11 minutes

Narrative arc: Start with three familiar loops, show their common patterns, and then introduce the corresponding array abstractions.

0:00–2:00 — Map

Narration: “Suppose we have five temperatures in Celsius. We want to convert each temperature to Fahrenheit. Each input produces exactly one output. This is a mapping operation. It preserves the structure of the array while transforming its elements.”

2:00–4:00 — Filter

Narration: “Now suppose we only want temperatures above freezing. We evaluate a condition for each value and keep the values that satisfy it. Unlike mapping, filtering can change the length of the result.”

4:00–6:00 — Reduce

Narration: “Next, suppose we want the highest temperature, or the sum of all temperatures. These are reductions. We combine elements using a function until we obtain a result. For a full reduction over a vector, the result is often a scalar.”

6:00–8:30 — Composition

Narration: “The interesting part is that these operations can be composed. Convert the temperatures, select those above a threshold, and calculate their average. We can describe the entire computation as a sequence of transformations.”

8:30–11:00 — X_eTaL preview

Narration: “X_eTaL includes the array-language idea of reduction. Its notation can express a reduction by addition with a compact function expression. We will learn how to read this syntax shortly. For now, concentrate on what the operation means.”

Video 05 — Broadcasting and Array Semantics
Target: 10 minutes

This episode should explicitly distinguish scalar extension from NumPy-style general broadcasting. They are not equivalent, and students should not assume that every array language automatically aligns arbitrary dimensions.

Narration for the key sequence:

“When we add the number ten to a vector, we can interpret the scalar as participating in an operation with every element. This is scalar extension. But what happens when we add a vector to a matrix? Different languages make different choices. Some implement elaborate broadcasting rules; others require shapes to match or transformations to be explicit. These decisions affect readability, error detection, and the meaning of programs.”

Show three animated cases: scalar plus vector, equal-shaped vectors, and incompatible arrays. Then demonstrate the actual X_eTaL behavior using executable examples from the repository.

The design rationale matters here: rather than treating NumPy conventions as universal, explain why X_eTaL's simpler scalar-extension policy can make operations more predictable.

Video 07 — APL, J, K, BQN, and X_eTaL
Target: 10 minutes

The lesson should introduce the language family without suggesting that X_eTaL is a direct replacement for any one member.

The central comparison should cover notation, evaluation direction, function composition, array structure, typing, and tooling.

Narration:

“APL demonstrated that a programming language could treat arrays and mathematical transformations as its fundamental vocabulary. J explored an ASCII-based notation and powerful function composition. K emphasized a compact vocabulary and concise expressions. BQN revisited many array-language ideas with a modern notation and combinators. X_eTaL takes inspiration from this family, but makes different choices: statically checked types, ASCII source with typographic rendering, and a deliberate emphasis on functional composition.”

Video 09 — Bindings, Values, and Immutability
Target: 9 minutes

The distinction between an immutable value and a mutable binding deserves careful treatment, especially because students arriving from Rust may assume the semantics are identical.

Narration script, central segment:

“When we create a value, we should distinguish that value from the name used to refer to it. A binding can associate a name with an array or tuple. Changing a binding is conceptually different from modifying the contents of the value itself.

Functional programming encourages us to treat values as immutable. Rather than changing an existing value in place, we derive a new value from it. This makes functions easier to reason about because their results depend on their inputs rather than on hidden modifications.

X_eTaL also has explicit facilities for mutation. We need to understand where mutation is permitted, what it means, and how to isolate it from the functional parts of a program.”

Visualize a tuple as a fixed structure and a binding as a labeled arrow pointing to it. Then animate rebinding the arrow to a new tuple without altering the original.

The exact rules for tuple-field mutation should be checked against the implementation before producing this episode, particularly if the planned immutability changes are adopted.

Video 10 — Functions as Values
Target: 11 minutes

The essential lesson is that functions are not merely procedures invoked by name. They can be values that are passed to other functions and used to construct computations.

Narration:

“In many introductory programming examples, a function is something we call. We give it arguments and receive a result. Functional programming adds another perspective: the function itself can be treated as a value.

We can pass a function to another function, store a function reference, or construct a new function from existing functions. This is the foundation of mapping, reduction, partial application, currying, and composition.

A reduction is a good example. The reduction operation doesn't need to know in advance whether we want addition, multiplication, minimum, or maximum. We supply the operation as an argument.”

The visual should represent functions as labeled transformation blocks and demonstrate that the same reduction structure can accept different operations.

Video 11 — Pipelines and Function Composition
Target: 11 minutes

This episode should compare conventional nested calls, a left-to-right pipeline, and an array-language composition.

Animated pipeline example


Narration:

“A pipeline describes a computation as a series of transformations. Each stage receives a value and produces a result that becomes the input to the next stage.

Function composition is closely related, but it is not exactly the same thing. A pipeline emphasizes the movement of values through operations. Composition constructs a new function from other functions, which can then be applied to values.

X_eTaL explores both ideas. Its notation supports composition and function trains, while macros can help express pipelines in a form that reads from left to right.”

The episode should also show when an intermediate named value improves readability and debugging compared with a single dense expression.

choose(true, expensive_computation(), 0)

7. Production architecture for Remotion and VoxCPM
I would treat the video course as a versioned, executable documentation project, not simply a collection of rendered videos.

The biggest risk is that X_eTaL is evolving. A video may accurately describe the language when produced but become outdated after a type-system or macro-system change.

The solution is to separate educational content, verified examples, narration, animation, and rendering.
